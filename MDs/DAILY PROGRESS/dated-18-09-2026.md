## 2. End-to-End Latency Analysis & Optimization

### Measured Bottlenecks in the Pipeline:
1. **FFmpeg Ingest Relay:** `analyzeduration 1000000` (1s) and `probesize 1000000` (1MB) introduced ~1s of unneeded demuxer buffering before passing the RTMP feed to MediaMTX via RTSP.
2. **MediaMTX HLS Segmenting:** Configured with `hlsVariant: mpegts`, `hlsSegmentDuration: 1s`, and `hlsSegmentCount: 3`, requiring a minimum 3-second buffer before the client starts decoding.
3. **Player Protocol Default:** `LivePlayer.tsx` defaulted to HLS (2–4s) on initial load, requiring viewers to manually toggle WebRTC (<500ms).
4. **HLS.js Client Buffering:** Defaulted to conservative VOD settings with 30s back buffer and no aggressive live-edge synchronization.
5. **Nginx Proxy Buffering:** Lacked `proxy_buffering off` and cache-control headers on `/hls/` and `/live/` proxy locations.

## 3. Implemented Optimizations

### 1. `nginx-rtmp/nginx.conf` (FFmpeg Ingest Relay Optimization)
- Added `-fflags nobuffer -flags low_delay` before input `-i`.

- Reduced `-probesize` from `1000000` (1MB) → `100000` (100KB).

## 7. Incident: MediaMTX API 401 & HLS/WebRTC Black Screen

- **Symptom:** Video was ingested and recorded by FFmpeg, but web dashboard displayed black screen. `curl http://127.0.0.1:9997/v3/paths/list` returned `401 Unauthorized` / `authentication error`, and `curl http://127.0.0.1:8888/live/73846/index.m3u8` returned `404 Not Found`.
- **Root Cause:** MediaMTX v1.12+ enforces internal authentication by default when no `authInternalUsers` block is defined. Anonymous readers/API callers are denied access, causing MediaMTX to hide paths and return 401/404.
- **Resolution:** Configured `authMethod: internal` with an explicit `user: any` entry granting `publish`, `read`, `playback`, `api`, and `metrics` permissions with no password. This allows anonymous access to public streams and local API endpoints while upstream security is enforced by `nginx-rtmp`'s `on_publish` database hook.
- **Status:** Fixed in `mediamtx.yml`.

## 8. WebRTC vs LL-HLS Cloudflare Architecture

- **WebRTC Black Screen Root Cause:** `live.dhanushuav.in` is routed through **Cloudflare Free Proxy (Orange Cloud)**. Cloudflare Free Proxy only proxies TCP HTTP/HTTPS (port 443) and drops raw UDP traffic (port 8889). WebRTC signaling succeeds over HTTPS, but video RTP UDP packets are dropped at Cloudflare edge. Result: WebRTC shows green pulse badge ("connected") but screen stays black.
- **Protocol Decision:** **LL-HLS is the primary protocol** for all public viewers over HTTPS port 443. With the optimizations applied today (800ms segments, liveSyncDurationCount: 1), LL-HLS achieves ~1.5s latency reliably through Cloudflare. WebRTC remains an option for local LAN / Tailscale users.
- **Resolution:** Reverted default `playerMode` in `LivePlayer.tsx` to `"hls"`.
- **Nginx-RTMP Relay Resync:** Restart `nginx-rtmp` so its internal FFmpeg relay reconnects to the newly recreated MediaMTX container.

## 9. HLS 404 Resolution, Video Loop Feature & IST Timezone

- **HLS 404 Root Cause:** MediaMTX `hlsVariant: lowLatency` requires partial chunk alignment matching GOP boundaries. When the drone streams with a standard 1s keyframe interval, MediaMTX fails to generate partial chunks and returns 404 on `index.m3u8`.
- **HLS Fix:** Reverted `hlsVariant` in `mediamtx.yml` to standard `mpegts` with 1s segments and 3 segment count. This instantly resolves the 404 error and serves the live HLS stream.
- **Video Loop Option Added:** Added a dedicated **Loop toggle button** (`Loop: ON / OFF`) in `RecordingPlayer.tsx` with a `Repeat` icon. Users can now continuously loop any flight video.
- **Flight Record Time (IST Fix):**
  - Added `TZ: Asia/Kolkata` to all services (`mediamtx`, `server`, `client`, `nginx-rtmp`) in `docker-compose.yml` so MediaMTX auto-recording files are named in Indian Standard Time.
  - Stored ISO timestamp in SQLite `recordings` table.
  - Forced `timeZone: "Asia/Kolkata"` formatting in `RecordingCard.tsx` so all flight times display in accurate IST.
