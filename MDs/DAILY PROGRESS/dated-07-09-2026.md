## 1. Issues Investigated

### DJI RS 2 Remote RTMP Streaming Failed in the Field

**User Report:**
- Tested live RTMP streaming from field using DJI RS 2 remote controller at 720p.
- After clicking "Live Streaming", countdown "3, 2, 1" completed.
- 3–4 seconds later, received an error notification on the remote: "RTMP streaming failed".
- Challenge: Drone and remote are only available during field operations, making live desktop debugging impossible without persistent diagnostics.

**Investigated Probable Causes:**
1. **Stream Key / URL Configuration Mismatch:** DJI GO 4 / RS 2 remote might be configured with an outdated path (`/ingest/` vs `/live/`), a mistyped 5-digit stream key, or an inactive stream key in SQLite DB.
2. **Auth Webhook Rejection (`401` or `403`):** MediaMTX calls `http://server:5011/api/hooks/auth` on every publish. If key lookup fails or IP filter fails, MediaMTX drops the drone immediately.
3. **Network / LTE Carrier Block (Port 1935):** If mobile network or SIM card blocks outbound TCP port 1935, the 3–4 second countdown expires with timeout without ever reaching Server 0149.
4. **MediaMTX Logs Ephemeral:** Without persistent file logging, past connection attempts in Docker are lost when inspecting after the fact.

## 5. Root Cause Discovery & Architectural Solution: Nginx-RTMP Relay

### Root Cause Discovered
During live field testing with the DJI RS 2 remote controller (stream key `77017`), MediaMTX logged:
```text
rtmp-mediamtx | [RTMP] is publishing to path 'live/77017'
rtmp-mediamtx | [RTMP] closed: received a packet for video track 0, but track is not set up
```

**Analysis:**
- DJI drones (RS 2, Mavic, Osmo) often emit raw video data packets before completing the formal codec sequence header (SPS/PPS NAL units).
- MediaMTX enforces strict packet ordering: receiving media packets prior to track setup causes MediaMTX to immediately abort the connection (`closed: received a packet for video track 0, but track is not set up`).
- The drone attempts to reconnect immediately, leading to the rapid 16-reconnection loop observed in the field diagnostics logs.

### Architectural Solution
To ensure bulletproof compatibility with all DJI drone hardware:
1. **`nginx-rtmp` Container (`rtmp-nginx-rtmp`):**
   - Built on `tiangolo/nginx-rtmp` with FFmpeg.
   - Listens on public RTMP port `1935`.
   - Uses lenient C-based RTMP socket handling that buffers and accommodates DJI connection timing.
2. **Backend Authentication Webhook (`/api/hooks/rtmp-auth`):**
   - Validates incoming stream keys against SQLite DB before permitting the stream.
   - Records field diagnostics in persistent logs.
3. **Lossless Stream Relay via RTSP (`exec_push`):**
   - Relays accepted streams to MediaMTX via RTSP TCP (`rtsp://mediamtx:8554/live/$name`).
   - FFmpeg re-packets the stream with complete SPS/PPS metadata headers, guaranteeing MediaMTX receives a valid track structure.
   - Zero transcoding CPU overhead (`-c copy`) for standard streams, and optional auto-transcoding for non-standard resolutions on the `ingest/` path.
4. **Clean Recording Finalization (`/api/hooks/on-unpublish-nginx`):**
   - Hooks into stream disconnection to trigger auto-recording registration and faststart optimization.

### Container Startup Optimization
- **Issue Investigated:** `rtmp-nginx-rtmp` entered crash loop with error: `/bin/sh: can't create /etc/nginx/nginx.conf: Read-only file system`.
- **Root Cause:** The base image's default entrypoint ran `envsubst` trying to write to the read-only volume-mounted `/etc/nginx/nginx.conf:ro`.
- **Fix:** Added `entrypoint: ["nginx"]` in `docker-compose.yml` to directly launch Nginx with the mounted config, preventing the write error and preserving internal Nginx variables like `$name`.
